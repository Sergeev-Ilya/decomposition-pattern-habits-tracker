# Трекер привычек — выбор стека

Статус: **пользователь утвердил вариант 1**. Основание — [согласованные требования](requirements.md), стек по умолчанию из [README](../README.md) и ответ пользователя «Подтверждаю вариант 1».

Ожидается до 10 пользователей без одновременной работы. Для выбора важнее простота реализации, сохранность истории и соответствие шаблонам проекта, чем различия в производительности фреймворков. Оценки сложности и сроков ниже — инженерное суждение применительно к этому репозиторию, без обещаний календарных сроков.

## Recommended (Default) — вариант 1

**React + Vite + TypeScript + Tailwind; Node.js + Express + TypeScript; PostgreSQL.**

| Слой | Выбор | Обоснование |
|---|---|---|
| Интерфейс | React, Vite, TypeScript, Tailwind | Подходит для списка привычек, календаря, форм входа и редактирования; совпадает со стеком прототипа и frontend в процессе проекта. |
| Backend | Node.js, Express, TypeScript | Совпадает с шаблонами backend; общий язык с интерфейсом упрощает сопровождение и согласование типов данных. |
| Хранение | PostgreSQL, отдельная база на сервис | Постоянное хранение аккаунтов и выполнений; ограничения уникальности и транзакции нужны для email, дат выполнения, лимита и удаления истории. Границы сервисов определяются на этапе архитектуры. |
| Аутентификация | Email и пароль; JWT | Соответствует требованиям и базовому стеку. Пароли хешируются; проверка владельца выполняется на сервере. Хранение токенов, сроки действия, обновление и завершение сессии будут определены при проектировании безопасности и API. |
| API | REST, OpenAPI 3.1 | Явные контракты для регистрации, входа, привычек, отметок и месячной статистики. |
| Входная точка API | Express API Gateway / BFF | Соответствует шаблонам проекта; детали маршрутизации определяются после выбора границ сервисов. |
| Backend-тесты | Vitest, supertest | Проверка бизнес-правил и HTTP API, включая граничные даты, изоляцию данных и удаление. |
| Frontend-тесты | Vitest, Testing Library, Playwright | Проверка компонентов и пользовательских сценариев в браузере с рабочим API. |
| Запуск | Docker Compose | Единое описание запуска приложения и баз данных. Локальное или серверное размещение выбирается после прототипа. |

Vite предоставляет шаблоны React с TypeScript и сборку статических ресурсов; Express описан как минимальный и гибкий Node.js-фреймворк. Это поддерживает выбор обычного клиентского приложения с отдельным API. [Vite](https://vite.dev/guide/), [Express](https://expressjs.com/).

Рекомендация — **вариант 1**: он соответствует существующим шаблонам и не требует менять технологический процесс ради небольшого сервиса. Основное внимание при реализации будет уделено календарным датам в часовом поясе пользователя, пересчёту серии, полному знаменателю месяца и сохранности данных.

## Alternative A — вариант 2: Fastify вместо Express

Интерфейс, PostgreSQL, JWT, REST/OpenAPI, тестирование и Compose остаются как в варианте 1; backend использует **Node.js + Fastify + TypeScript**. Входную точку API можно сохранить на Express, как в шаблоне; её детали определяются на этапе архитектуры.

Fastify поддерживает TypeScript и проверку запросов по схемам. Это удобно, если команда предпочитает строить обработчики вокруг схем данных. Потребуется адаптировать Express-ориентированные шаблоны и HTTP-тесты. Для нагрузки до 10 пользователей выбирать его ради скорости оснований нет. [TypeScript в Fastify](https://fastify.dev/docs/latest/Reference/TypeScript/), [валидация и сериализация](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/).

## Alternative B — вариант 3: Next.js вместо Vite

Интерфейс использует **Next.js + React + TypeScript + Tailwind**; отдельный Express backend, PostgreSQL, JWT, REST/OpenAPI, gateway и Compose сохраняются. Vitest, Testing Library и Playwright остаются инструментами проверки; конфигурация адаптируется к Next.js.

Next.js подходит при предпочтении его маршрутизации и модели приложения либо при будущей потребности в серверных возможностях интерфейса. Согласованный личный кабинет сейчас не требует серверного рендеринга. Переход с Vite-прототипа потребует адаптации структуры и сборки.

Next.js допускает статический экспорт на обычный файловый веб-сервер. При использовании возможностей, требующих выполнения на сервере, нужно соответствующее окружение; утверждать, что любой вариант Next.js обязательно требует отдельный Node.js-процесс для frontend, неверно. [Официальная документация статического экспорта](https://nextjs.org/docs/pages/guides/static-exports).

## Сравнение вариантов

| Критерий | 1. Vite + Express | 2. Vite + Fastify | 3. Next.js + Express |
|---|---|---|---|
| Соответствие шаблонам | Прямое | Нужна адаптация backend | Нужна адаптация frontend |
| Сложность первой версии | Базовая для этого проекта | Дополнительная настройка схем и backend | Дополнительные решения о режиме сборки и структуре frontend |
| Путь к MVP | Наиболее прямой в этом репозитории | Дольше при отсутствии готовых Fastify-шаблонов | Дольше при переносе Vite-прототипа |
| Соответствие нагрузке до 10 пользователей | Достаточно по характеру задачи; проверяется тестами | Не даёт необходимого требованиями преимущества | Не даёт необходимого требованиями преимущества |
| Потенциал развития | Дальнейшие изменения по реальной потребности | Удобен при предпочтении схем Fastify | Полезен при потребности в возможностях Next.js |
| Знакомство команды | Предпочтения пользователя не заявлены; шаблоны проекта готовы | Предпочтения не заявлены | Предпочтения не заявлены |

Микросервисная организация и отдельные базы следуют процессу этого репозитория, а не нагрузке в 10 пользователей. Количество и ответственность сервисов здесь не фиксируются. Ни один вариант не требует брокера сообщений, Redis, очередей, Kubernetes, почтовой инфраструктуры или OAuth для согласованного MVP.

Точные версии зависимостей будут выбраны и закреплены при реализации после проверки совместимости и поддержки. Этот документ не фиксирует непроверенные номера версий.
