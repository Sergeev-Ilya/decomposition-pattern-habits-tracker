# habits-service — схема БД и транзакции

**База:** `ritm_habits`, отдельный PostgreSQL и именованный том `habits_data`. Контракты: [api.yaml](api.yaml), [архитектура](../architecture.md), [внутренняя проверка сессии](../auth-service/api.yaml).

UUID PK, `snake_case`, `created_at`/`updated_at` типа `timestamptz` на всех таблицах. Календарные значения хранятся как PostgreSQL `date` и выдаются строкой `YYYY-MM-DD`, без преобразования в локальный timestamp. DTO — camelCase. Все FK находятся внутри этой базы.

## Таблицы

### `habit_owners`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | uuid | PK; подтверждённый auth-service UUID пользователя, не генерируется независимо |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() |

Строка — локальный ключ сериализации операций лимита, не копия аккаунта. Создаётся при первом обращении через `INSERT ... ON CONFLICT DO NOTHING`. Не содержит email, пароль, часовой пояс или JWT. Значение `id` — логическая ссылка на `auth.users.id`, без межсервисного FK.

### `habits`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | uuid | PK DEFAULT gen_random_uuid() |
| `user_id` | uuid | NOT NULL FK habit_owners(id), владелец |
| `name` | varchar(120) | NOT NULL, trim, CHECK char_length(name) BETWEEN 1 AND 120 |
| `description` | varchar(2000) | NOT NULL DEFAULT '', trim, максимум 2000 символов |
| `start_date` | date | NOT NULL, вычисляется сервером при создании, неизменяемая |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() |

CHECK `name = btrim(name)` и `description = btrim(description)`; приложение согласованно trim-ит Unicode-пробелы до записи. Длины проверяются как Unicode-кодовые точки (не UTF-16 code units). API принимает только `name` и `description`, не `userId`, `startDate`, цвет, иконку или категорию. `null` не является строкой и отклоняется. `PATCH` требует хотя бы одно из двух полей, отсутствующее поле не меняется, `description:''` очищает описание.

Индекс `habits_user_created_idx (user_id, created_at, id)` обеспечивает выборку владельца и стабильный порядок `created_at ASC, id ASC`. Лимит 25 защищается транзакциями ниже, не отдельным неточным счётчиком. `user_id`, `start_date`, `created_at` не изменяются редактированием. `updated_at` меняется при фактическом изменении названия/описания или отметок.

### `completions`

| Поле | Тип | Ограничения / назначение |
|---|---|---|
| `id` | uuid | PK DEFAULT gen_random_uuid() |
| `habit_id` | uuid | NOT NULL FK habits(id) ON DELETE CASCADE |
| `completed_on` | date | NOT NULL, календарная дата выполнения |
| `created_at` | timestamptz | NOT NULL DEFAULT now() |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() |

UNIQUE `completions_habit_date_key (habit_id, completed_on)` одновременно защищает идемпотентную установку и индексирует календарь/серии. Отсутствие строки означает невыполнение. Старые отметки не удаляются по возрасту; их изменение ограничивается API. Выполнения не могут предшествовать `start_date` или быть будущими при записи: это проверяется в транзакции после блокировки привычки. CHECK с текущим временем не создаётся.

Серия, месячный процент, число привычек и `todayCompleted` не хранятся как независимые счётчики. Иконки и цвет — локальное оформление frontend по стабильному идентификатору, не новые доменные поля.

## Авторизация каждого запроса

1. Из единственной cookie `ritm_session` извлекается JWT. Проверяются разрешённый HS256, подпись общим signing secret, `iss=ritm-auth`, `aud=ritm-app`, `iat/exp`, UUID `sub/sid`. Отсутствующий/дублирующийся/невалидный JWT даёт `401 UNAUTHENTICATED`.
2. На каждом защищённом запросе без кэша вызывается `POST auth-service/internal/sessions/verify` с `X-Service-Key: INTERNAL_SERVICE_KEY`, JSON `{token}`. Это отдельный ключ, не signing secret. Подтверждённые `userId/sessionId` обязаны совпасть с `sub/sid`; `timeZone` берётся из ответа auth-service и проверяется как поддерживаемая IANA-зона. Некорректный ответ, timeout, ошибка соединения, внутренний 403 или сбой auth-БД дают `503 SERVICE_UNAVAILABLE`, не успешный доступ. Внутренний 401 преобразуется в публичный 401.
3. Все выборки привычки используют одновременно `id` и подтверждённый `user_id`. Невалидный UUID — 400; валидный UUID чужой/удалённой/неизвестной привычки — одинаковый `404 HABIT_NOT_FOUND`. Переданные клиентом owner, timezone, `X-User-*` и часы не участвуют в авторизации.
4. Публичные POST/PATCH/PUT/DELETE требуют `Origin = APP_ORIGIN` и JSON для непустого тела. Общая ошибка — `{error:{code,message,details?},requestId:UUID}`. Личные ответы имеют `Cache-Control: no-store`.

## Транзакционные операции

Обычный уровень PostgreSQL `READ COMMITTED` используется вместе с явными row locks. После ожидания блокировки заново берётся серверное время и одна дата `D` в подтверждённой IANA-зоне; публичный API не принимает тестовые часы.

### Создание и лимит

В одной транзакции: создать `habit_owners`, если отсутствует; получить её `FOR UPDATE`; посчитать существующие `habits WHERE user_id=$user`; при 25 вернуть `409 HABIT_LIMIT_REACHED` без вставки, иначе вычислить `start_date=D` и вставить привычку. Ответ `201 {habit,today,timeZone}` формируется из подтверждённого состояния. Два одновременных создания при 24 привычках дают одну успешную вставку и один 409.

### Редактирование

В транзакции выбрать свою привычку `FOR UPDATE`, заменить только переданные `name/description`; историю и начало не менять. Вернуть `200 {habit,today,timeZone}`. No-op редактирование может сохранить прежний `updated_at`.

### Удаление

Порядок блокировок: локальная строка владельца, затем принадлежащая ему привычка. Удалить привычку; FK каскадно удаляет все выполнения той же транзакцией. Коммит предшествует `204`, слот освобождается сразу. Отсутствующая/чужая привычка даёт 404. Восстановления, soft delete и архивирования нет; подтверждение — диалог frontend, не флаг API.

### Установка/снятие выполнения

В транзакции выбрать свою привычку `FOR UPDATE`, повторно определить `D`, проверить существование григорианской даты и окно `[max(start_date,D−7),D]` включительно.

- `completed:true`: `INSERT ... ON CONFLICT (habit_id,completed_on) DO NOTHING`.
- `completed:false`: удалить строку этой даты, если есть. Отсутствующая строка — допустимый no-op, но только внутри разрешённого окна.
- Серверного toggle нет. Повтор одного желаемого состояния не переворачивает отметку и всегда даёт `200` с подтверждённым `completed`.
- При фактическом изменении обновить `habits.updated_at`; пересчитать summary в той же транзакции, использовать ту же `D` для ответа. Frontend затем перечитывает выбранный календарь.

Синтаксически неправильная или невозможная дата — `400 VALIDATION_ERROR`; реальная дата вне окна, включая дату до создания и будущую, — `400 DATE_NOT_EDITABLE`. Установка и снятие имеют одинаковые ограничения. Разница дат считается календарной арифметикой, без деления миллисекунд на 24 часа.

## Чтение и вычисления

Каждый ответ использует одну серверную дату `D`, а несколько SQL-выборок одного календарного ответа выполняются в read-only транзакции `REPEATABLE READ`, чтобы habit, marks и статистика отражали один снимок. При ожидаемой небольшой нагрузке отдельный cache/read model не нужен.

| Ответ | Данные |
|---|---|
| `GET /api/habits` | `{habits:HabitSummary[],today,timeZone,limit:25}`; максимум 25, stable order |
| `GET /api/habits/{id}` | `{habit:HabitSummary,today,timeZone}` |
| `GET /api/habits/{id}/calendar?month=YYYY-MM` | `{habit,month,completedDates,completedCount,daysInMonth,completionPercent,editableFrom,editableTo,today,timeZone}` |
| `PUT .../completions/{date}` | `{habit,date,completed,today,timeZone}` |

`HabitSummary` содержит `id,name,description,startDate,createdAt,updatedAt,currentStreak,todayCompleted,recentCompletedDates`. Последнее поле содержит только выполненные даты `[D−6,D]`, не ранее начала, максимум 7, уникальные и отсортированные. Полная многолетняя история в list/detail/mutation не передаётся; сервер использует её только для вычисления серии. API не доверяет вычислениям браузера.

Текущая серия: цепочка назад от D, если D выполнен; иначе от D−1, если вчера выполнено; иначе 0. Переходит через границы месяца/года и заканчивается не ранее `start_date`. Её можно вычислить SQL-поиском непрерывной цепочки или ограниченным чтением дат до первого пропуска; возвращать все даты клиенту не нужно.

Для календаря отсутствующий `month` означает текущий. Строгий формат `YYYY-MM`, год 0001..9999, месяц 01..12; месяц должен быть не раньше месяца начала и не позже текущего. Неверный формат — `400 VALIDATION_ERROR`, вне диапазона — `400 MONTH_OUT_OF_RANGE`. Frontend по согласованной спецификации заменяет некорректный URL на текущий месяц и запрашивает его. `completedDates` — только выбранный месяц, максимум 31. Числитель — количество этих дат; знаменатель — полное число дней месяца, даже текущего/месяца создания. `completionPercent = completedCount / daysInMonth * 100` без предварительного округления; UI показывает один десятичный знак. Месяц без выполнений имеет 0%.

`editableFrom=max(start_date,D−7)`, `editableTo=D` — общее окно привычки, не обрезанное выбранным месяцем. При просмотре прошлого месяца, который не пересекается с окном, все его даты readonly. Серия в календарном ответе остаётся сегодняшней.

Парсер календарной даты обязан проверять точный round-trip года/месяца/числа, включая високосный февраль; нормализация 30 февраля в март не допускается. Тесты внедряют часы в сервис, проверяют D−7/D−8, дату создания, будущую дату, DST, конец месяца/года и високосный февраль; API поля `today`, `timeZone`, `startDate` во входном JSON отклоняются.

## Миграции и сохранность

`001_init.sql`: три таблицы, локальные FK, CHECK/UNIQUE и индексы. Применённые миграции версионируются; повторный запуск ничего не очищает. `GET /health` возвращает `200 {status:"ok",service:"habits-service"}` после миграций и успешного запроса к собственной БД, иначе 503. Недоступность auth-service не маскируется readiness БД: реальные защищённые запросы всё равно fail closed с 503.

Именованный том `habits_data` сохраняет привычки и отметки между пересозданиями контейнеров. Данные не очищаются при смене месяца, года, рестарте или выходе пользователя; только явное удаление привычки удаляет её историю.
