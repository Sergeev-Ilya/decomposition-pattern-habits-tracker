## Исправленная регрессия

В email принимались ASCII-управляющие символы, включая NUL. Регрессионный тест воспроизвёл `503` вместо ожидаемого `400`: недопустимая строка доходила до PostgreSQL. Проверка email теперь отклоняет диапазоны U+0000–U+001F и U+007F до обращения к базе. Добавлен один тест для регистрации и входа; нормализация email и отсутствие trim у пароля сохранены.

Исправление: [auth-service/src/app.ts](../backend/auth-service/src/app.ts). Регрессионное покрытие: [auth.test.ts](../backend/auth-service/tests/auth.test.ts). Полный auth-набор и сборка выполнены после изменения.

## Команды

Из `backend/auth-service/`:

```bash
npm run build
TEST_DATABASE_URL=postgresql://ritm_test:ritm_test_only@127.0.0.1:55431/ritm_auth_test npm test
```

Из `backend/habits-service/`:

```bash
npm run build
TEST_DATABASE_URL=postgresql://ritm_test:ritm_test_only@127.0.0.1:55432/ritm_habits_test npm test
```

Из `backend/api-gateway/`:

```bash
npm run build
npm test
```

`ritm_test_only` — намеренно открытый пароль изолированных временных тестовых контейнеров, не учётные данные приложения. Доменные suites используют только базы с суффиксом `_test`; рабочие базы не очищались и не подменялись тестовыми fixtures.

После исправления только auth-service пересобран и перезапущен из `backend/`:

```bash
docker compose up -d --build --wait --wait-timeout 120 auth-service
```

Команда завершилась с exit 0, auth-service и его БД healthy. Рабочие конфигурация и именованные тома сохранены. Затем выполнен [межсервисный сценарий](../backend/tests/cross-service-smoke.mjs) из `backend/`:

```bash
docker compose exec -T api-gateway node --input-type=module < tests/cross-service-smoke.mjs
```

## Межсервисное подтверждение

Сценарий обращался к `http://api-gateway:8080` внутри сети Compose с согласованным Origin `http://localhost:8880`. Подтверждены:

- общая readiness двух сервисов, `401` без сессии и недоступность внутреннего verify через публичный gateway;
- регистрация без автоматического входа, вход с HttpOnly-cookie и восстановление профиля через сохранённую сессию;
- пустой список нового пользователя, создание привычки с серверной датой, выполнение, повторная идемпотентная запись и текущая серия;
- календарь с процентом от полного числа дней месяца и сохранение истории после редактирования;
- изоляция второго пользователя, в том числе при подставленном заголовке владельца;
- удаление привычки и недоступность её истории, освобождение места в списке;
- отзыв сессии, очистка cookie и отказ в использовании сохранённого JWT как через auth-service, так и через реальную межсервисную проверку habits-service.

Сценарий создавал только уникальные синтетические аккаунты. Его привычка удалена через API, обе созданные сессии завершены; аккаунты могут оставаться в рабочей БД. Прямое изменение схемы или очистка рабочих данных не выполнялись. JWT, пароли, email fixtures и секреты окружения в вывод не включались.

Серверные исторические, DST, високосные и конкурентные граничные случаи покрыты доменными suites на отдельных тестовых БД с внедряемыми часами. Рабочий API не получал тестового управления датой.

`state.tests.backend` установлен по этому отчёту. Этот сценарий не подменяет последующие проверки: итоговый браузерный origin, сохранность и E2E подтверждены отдельно в [deploy-log.md](deploy-log.md) и [frontend-test-report.md](frontend-test-report.md). Временные тестовые контейнеры после завершения остановлены; их можно снова запустить командой `docker start ritm-auth-test-db ritm-habits-test-db` перед повторением доменных тестов.
